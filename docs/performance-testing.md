# Проверка скорости тестовой сборки

1. Закройте Antigravity. Запустите новую сборку и выберите **1. Включить обход**, чтобы обновить установленную DNS-службу. Затем запустите Antigravity заново.
2. Сначала проверьте обычную работу с теми же моделью и запросом, с которыми наблюдалась задержка.
3. Для сравнения откройте **8. Сравнить скорость ответов** (команда `speed`). Выберите профиль приложения и маршрут: основной Cloud Code или daily, затем IP из найденных кандидатов.
4. Между маршрутами полностью закрывайте и запускайте Antigravity. Для каждого прогона используйте новый чат, одну модель и одинаковый запрос. Не меняйте сеть, VPN, инструменты и объём контекста внутри одного сравнения.
5. После запроса внесите время от отправки до первого текста и до полного ответа. Можно дополнительно указать число символов ответа и замеченные повторы. Ошибки и обрывы записывайте как неудачный прогон.
6. Выполните минимум три прогона каждого из хотя бы двух маршрутов. Лучше чередовать варианты, чтобы нагрузка сервиса в разное время меньше влияла на сравнение. Пункт сравнения покажет медианы и предложит маршрут: сначала меньше ошибок и повторов, затем меньше ожидание первого текста и полного ответа.

Это ручные измерения реальных запросов в IDE. Программа не отправляет запросы к модели и не измеряет токены автоматически. Оценка символов в секунду приблизительная; она зависит от длины ответа и точности измерения времени. Для другой модели или запроса начните новое сравнение. Если маршрут изменился при восстановлении подключения, программа отклонит результат, когда обнаружит это при вводе.

Выбор хранится локально и имеет приоритет до шести часов при том же подключении, пока маршрут доступен. После снятия приоритета исправный текущий маршрут сохраняется. Обнаруженный сетевой или региональный отказ разрешает переключение. Настройка endpoint применяется к выбранному профилю IDE; CLI в сравнении не участвует. Пользовательский нестандартный endpoint не заменяется.

Без запуска сравнения сборка тоже использует изменения DNS и фонового восстановления: готовые ответы не ждут сетевых проверок, запросы одного имени объединяются, отказ запасного IP не вызывает общий поиск. Полный периодический поиск выполняется раз в 15 минут; основной маршрут проверяется чаще. Первая проверка неизвестного или утратившего актуальность маршрута по-прежнему может потребовать обращения к сети.
